1.2 Chosen Business Scenario

We selected a Mobile Phone Repair and Servicing Center named FixSphere. In this business, customers bring broken mobile phones (broken screens, battery drainage, water damage, port issues). FixSphere manages the complete intake, diagnosis, repair assignment, and billing process.

The Problem with Manual Systems: Small repair shops often use paper notebooks. This leads to lost customer contact numbers, confusion about which technician is repairing which phone, mistakes in billing, and no security permissions between front-desk staff and technicians.

FixSphere Desktop Solution: A multi-role desktop application built in Visual Studio using C++/CLI and a real MySQL database. It secures the business through 3 roles:
  • Admin: Has full control — can register users, assign jobs to technicians, delete jobs, and view total revenue reports.
  • Checker: Front-desk staff — registers customers, takes in new phone repair jobs, and searches records. Cannot change repair statuses or assign jobs.
  • Repairer: Technician — can only see and update jobs assigned to their own account, set diagnoses, and input repair costs in Sri Lankan Rupees (LKR).

3. Worked Examples of Each OOP Pillar from FixSphere Code

The assignment requires demonstrating all 6 OOP concepts using real code written in our application: (1) Class, (2) Object, (3) Encapsulation, (4) Abstraction, (5) Inheritance, and (6) Polymorphism.

3.1 Pillar 1: Class

Concept: A class is a blueprint or template that defines variables (attributes) and functions (behaviors).

Code Example from Models.h:

// Class blueprint for Customer inheriting common person details
public ref class Customer : public Person
{
private:
    String^ address;

public:
    // Constructor initializing customer fields
    Customer(int id, String^ name, String^ contact, String^ nic, String^ address)
        : Person(id, name, contact, nic)
    {
        this->address = address;
    }

    property String^ Address
    {
        String^ get() { return address; }
        void set(String^ value) { address = value; }
    }
};

Explanation: The Customer class defines what data a customer holds (such as their home address) and what actions they can perform.

3.2 Pillar 2: Object

Concept: An object is an actual instance of a class created in computer memory during program execution using the gcnew keyword.

Code Example from LoginForm.h and MainForm.h:

// Creating a concrete UserSession object when an employee logs in
UserSession^ session = gcnew UserSession(empId, fullName, username, role);
UserSession::CurrentUser = session;

// Creating a concrete Customer object dynamically in memory
Customer^ custObj = gcnew Customer(1, L"Kamal Perera", L"0771234567", 
                                   L"200012345678", L"Anuradhapura");

Explanation: Here, session and custObj are real objects created in memory with specific personal values.

3.3 Pillar 3: Encapsulation

Concept: Encapsulation keeps internal data safe by making fields private and allowing access only through controlled public properties (getters/setters).

Code Example from Models.h:

public ref class Person abstract
{
private:
    // Private fields: cannot be modified directly from outside
    int id;
    String^ name;
    String^ contact;
    String^ nic;

public:
    // Controlled public property for Contact
    property String^ Contact
    {
        String^ get() { return contact; }
        void set(String^ value) 
        { 
            if (!String::IsNullOrWhiteSpace(value))
                contact = value; 
        }
    }
};

Explanation: Other parts of the program cannot accidentally corrupt contact or name because the variables are private. They can only be accessed through safe properties.

3.4 Pillar 4: Abstraction

Concept: Abstraction hides complex internal implementation details and shows only the essential interface to the user.

Code Example 1 (Abstract Class & Pure Virtual Method in Models.h):

public ref class Person abstract
{
public:
    // Pure abstract method: enforces every child class to implement its own role logic
    virtual String^ GetRoleDescription() abstract;
};

Code Example 2 (Hiding Database Complexity in DatabaseService.h):

// In the UI form, the developer simply calls this one-line abstraction:
DataTable^ dt = DatabaseService::ExecuteQuery(
    "SELECT * FROM repair_jobs WHERE status = @st", params);

Explanation: The UI form does not know how connection strings, MySQL sockets, open/close connections, or command objects work. All of that complex low-level work is completely hidden behind DatabaseService.

3.5 Pillar 5: Inheritance

Concept: Inheritance allows a new class (child class) to inherit variables and methods from an existing class (parent class), avoiding duplicate code.

Code Example from Models.h:

// Employee inherits common personal attributes from Person base class
public ref class Employee : public Person
{
private:
    String^ role;
    String^ username;
    bool isActive;

public:
    // Calls the base Person constructor using : Person(id, name, contact, nic)
    Employee(int id, String^ name, String^ contact, String^ nic, 
             String^ role, String^ username, bool isActive)
        : Person(id, name, contact, nic)
    {
        this->role = role;
        this->username = username;
        this->isActive = isActive;
    }
};

Explanation: Both Customer and Employee inherit id, name, contact, and nic directly from Person without having to write those fields twice.

3.6 Pillar 6: Polymorphism

Concept: Polymorphism means "many forms". It allows derived classes to provide their own version of a virtual method using the override keyword, called dynamically at runtime.

Code Example from Models.h:

// 1. Customer provides its own implementation
virtual String^ Customer::GetRoleDescription() override
{
    return L"Client / Device Owner requiring phone hardware or software servicing.";
}

// 2. Employee provides a completely different implementation of the same method
virtual String^ Employee::GetRoleDescription() override
{
    return String::Format(L"Internal Staff Member operating under role: {0}", role);
}

// 3. Runtime Polymorphic Behavior:
Person^ personRef = gcnew Employee(1, L"Admin", L"0770000000", L"199000000000", 
                                    L"Admin", L"admin", true);
String^ desc = personRef->GetRoleDescription(); // Calls Employee's method dynamically

Explanation: Even though personRef is a base Person^ pointer, the program calls the specific Employee method at runtime.

5.3 Sri Lankan Rupees (LKR) Financial Calculations

In accordance with business requirements, all repair costs and monthly financial revenue reports are strictly calculated and displayed in Sri Lankan Rupees (LKR): 

// SQL Query calculating monthly revenue exclusively for Finished jobs in LKR
SELECT COALESCE(SUM(cost), 0) AS total_revenue 
FROM repair_jobs 
WHERE status = 'Finished' 
  AND MONTH(COALESCE(finished_at, created_at)) = @selectedMonth
  AND YEAR(COALESCE(finished_at, created_at)) = @selectedYear;

// Formatted in C++/CLI UI:
lblMonthlyIncome->Text = String::Format(L"LKR {0:N2}", totalRevenue);

Business Rule: Only jobs with status Finished are counted towards monthly income. Jobs that are Pending, In Progress, or Couldn't Repair are strictly excluded or have a cost of LKR 0.00.
